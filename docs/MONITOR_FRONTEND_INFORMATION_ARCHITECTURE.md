# 監視フロントエンド情報設計

## 1. 目的

本ドキュメントは、OurA Navi Monitor 次期フロントエンド改修における情報設計、表示名、指標定義、チャート口径、エクスポート仕様、ユーザー詳細、チャット記録確認項目を固定するための設計文書です。

本モニターの主利用者は、開発者ではなく運用管理者です。画面上の文言はビジネス日本語を基本とし、最初に見る画面では技術フィールド名ではなく、運用判断に必要な意味を優先して表示します。Raw payload、技術イベント項目、詳細な governance / evidence 情報は BigQuery、エクスポート、または制限付き調査導線に保持しますが、第一階層の画面には過度に表示しません。

## 2. 画面階層

MVP の第一階層は `ダッシュボード` に集約します。主目的は、非技術管理者が一画面でシステム状態、回答品質、利用環境、追問状況、ユーザー別リスクを確認できることです。

独立した第一階層ナビゲーションとして `回答品質`、`連続質問分析`、`チャット記録確認`、`データ健全性` は置きません。回答品質と連続質問分析はダッシュボード上のセクションとして表示します。ユーザー単位の深い確認、会話・メッセージ確認、品質詳細は `ユーザー一覧` の `詳細` から `ユーザー詳細` へドリルダウンして確認します。

| 画面 / 領域 | フロントエンドでの扱い | 目的 |
| --- | --- | --- |
| `ダッシュボード` | 第一階層の唯一の主要画面 | KPI、利用環境・モード、利用推移、活性度、ユーザー一覧、回答品質、連続質問を表示する。 |
| `ユーザー一覧` | ダッシュボード下部セクション | ユーザー別の利用状況とリスクを確認し、`詳細` へ遷移する。 |
| `ユーザー詳細` | ユーザー一覧からのドリルダウン画面 | 単一ユーザーの摘要、品質、追問、会話一覧、メッセージ確認を行う。 |
| `会話・メッセージ確認` | ユーザー詳細内の drawer / lower panel | 選択ユーザーの conversation / message chain を preview-first で確認する。 |
| `チャット記録確認` | 独立フロントエンドページにはしない | API、BigQuery、export、内部調査用の能力として保持する。 |
| `データ健全性` | 独立フロントエンドページにはしない | schema / join / delay は backend monitoring、Cloud Logging、BigQuery、運用者向け export で確認する。 |

将来、専門運用者向けの advanced console が必要になった場合のみ、`チャット記録確認` と `データ健全性` を制限付きページとして追加します。MVP では表示しません。

## 3. 共通期間フィルター

初期表示は `今日` とします。

| 表示名 | 意味 |
| --- | --- |
| `今日` | 日本時間の当日。 |
| `直近6時間` | 現在から直近6時間。 |
| `直近12時間` | 現在から直近12時間。 |
| `過去3日` | 過去3日間。 |
| `過去7日` | 過去7日間。 |
| `過去14日` | 過去14日間。 |
| `過去30日` | 過去30日間。 |
| `過去60日` | 過去60日間。 |
| `全部` | monitor retention 内の全期間。 |
| `カスタム` | 管理者が任意に指定する期間。 |

ダッシュボード上部のグローバル期間選択では `カスタム` は表示しません。`カスタム` は export dialog と API 互換用に保持します。

分析口径が異なる `利用推移` と `活性度分布` では、セクション単位の期間選択を持たせます。選択肢は `3日`、`7日`、`14日`、`30日`、`全部` とし、初期値は `7日` です。

## 4. KPIサマリー

トップ KPI には `総リクエスト数` を表示しません。KPI は以下の5項目に限定します。

各 KPI カードには小さな円形の `?` ボタンを配置します。説明は hover で表示し、非技術者にも分かる説明を優先します。schema 名やフィールド名を主説明にしません。

| KPI表示名 | 管理者向け説明 | バックエンド計算メモ |
| --- | --- | --- |
| `アクティブユーザー数` | 選択した期間内に実際にチャットを利用したユーザー数です。 | 選択期間内に message または ask activity があるユーザーを集計する。 |
| `回答成功率` | エラー表示がなく、ユーザーからの回答再生成・回答強化・修正要求・低評価が確認されていない回答の割合です。 | error status、再生成要求、回答強化要求、修正要求、bad feedback がある回答を除外する。後から feedback が付与された場合は再集計可能にする。 |
| `低カバレッジ率` | 根拠資料や引用が不足している可能性がある回答の割合です。 | `coverage_gap_workitem_json`、`citation_count = 0`、`evidence_sufficiency = insufficient`、または `coverage_score` が閾値未満の回答を対象にする。 |
| `エラー率` | 回答生成や通信処理でエラーになった割合です。 | HTTP/server error と message-level error を可能な範囲で統合する。内訳はエクスポートで確認できるようにする。 |
| `P95応答時間` | 利用者の大半が待つ最大に近い応答時間の目安です。数値が大きいほど体感が遅くなります。 | 選択期間の応答時間95パーセンタイル。 |

初期の低カバレッジ閾値案は `coverage_score < 0.60` とします。ただし第一階層の UI 説明には閾値を直接表示せず、技術メモまたはエクスポート metadata 側に保持します。

## 5. ダッシュボード構成

ダッシュボードの表示順は以下で固定します。

1. `KPIサマリー`
2. `利用環境・モード分析`
3. `利用推移`
4. `活性度分布`
5. `ユーザー一覧`
6. `回答品質分析`
7. `連続質問分析`

この順序は、管理者が「全体状態を確認する」「利用状況を把握する」「品質を確認する」「影響ユーザーを特定する」という流れで確認できるようにするためです。

## 6. 利用推移

### 6.1 `利用推移`

初期表示は7日間です。選択肢は `3日`、`7日`、`14日`、`30日`、`全部` とします。グローバル期間とは独立して切り替えます。

| 表現 | 表示名 | 定義 |
| --- | --- | --- |
| 縦棒 | `アクティブユーザー数` | 日別のアクティブユーザー数。 |
| 折れ線 | `メッセージ数` | 日別のメッセージ数。 |

このグラフでは `リクエスト数` と `会話数` は表示しません。

### 6.2 `活性度分布`

円グラフで表示し、中央に `総ユーザー数` を表示します。

表示期間は `3日`、`7日`、`14日`、`30日`、`全部` から選択します。初期表示は7日間です。凡例は `%（人数）` 形式で表示します。

ユーザー一覧の `活性度区分` は直近7日列口径で固定します。円グラフ側は選択された表示期間に基づく分布として扱います。

| 活性度区分 | 定義 |
| --- | --- |
| `高アクティブ` | 表示期間内の利用頻度が高いユーザー |
| `中アクティブ` | 表示期間内に一定の利用があるユーザー |
| `低アクティブ` | 表示期間内の利用が少ないユーザー |
| `休眠ユーザー` | 表示期間内にメッセージ送信がないユーザー |

ツールチップ説明:

```text
選択した表示期間内の利用頻度に基づき、ユーザーを高・中・低・休眠に分類しています。
```

## 7. 利用環境・モード分析

セクション名は `利用環境・モード分析` とします。

3つのグラフは同じ期間選択を共有します。初期表示は `今日` とし、選択肢は `過去3日`、`過去7日`、`過去14日`、`過去30日` とします。

| 位置 | グラフ名 | 表現 | 定義 |
| --- | --- | --- | --- |
| 左 | `時間帯別リクエスト数` | 折れ線 | `00:00` から `23:59` までの時間帯別リクエスト数。複数日を選択した場合も時間帯ごとに累計して表示する。 |
| 中央 | `利用デバイス分布` | 円グラフ | 選択期間内の利用デバイス比率。 |
| 右 | `利用モード分布` | 円グラフ | 選択期間内の利用モード比率。 |

フロントエンド表示名:

| Raw value | 表示名 |
| --- | --- |
| `internal` | `社内モード` |
| `websearch` | `Web検索モード` |
| `desktop` | `PC` |
| `mobile` | `モバイル` |
| `unknown` | `不明` |

MVP の利用モード分布では `internal` と `websearch` を必須対象とします。その他の mode は、管理者向けの意味が確定するまで `その他` に集約できます。

## 8. 回答品質

セクション名は `回答品質分析` とします。

初期表示は `今日` とし、選択肢は `過去3日`、`過去7日`、`過去14日`、`過去30日` とします。

| 表示名 | 主な source | 表示意図 |
| --- | --- | --- |
| `回答可能性` | `answerability_level` | ユーザーの依頼に回答できているかを確認する。 |
| `回答利用可能性` | `usability_level` | 大きな修正なしに回答を利用できるかを確認する。 |
| `業務利用可能性` | `delivery_readiness` | 業務利用できる状態かを確認する。 |
| `根拠十分性` | `evidence_sufficiency` | 回答に十分な根拠があるかを確認する。 |

画面ではビジネス日本語の表示名を使用します。`verification_verdict`、`coverage_score`、`alignment_score`、`structured_led`、citation binding diagnostics などの技術項目は計算、エクスポート、将来の詳細画面で利用し、第一階層の表示名にはしません。

## 9. 連続質問分析

セクション名は `連続質問分析` とします。

初期表示は `今日` とし、選択肢は `過去3日`、`過去7日`、`過去14日`、`過去30日` とします。

| 表示名 | 定義 | 主な source |
| --- | --- | --- |
| `追問認識数` | 追問として認識された turn 数。 | `followup_open_result_json.event = recognized` または normalized follow-up resolution。 |
| `追問成功率` | 追問認識後、文脈を正常に引き継げた割合。 | `success_count / recognized_count`。 |
| `明示的な訂正` | ユーザーが前回文脈または回答内容を明確に訂正した turn 数。 | `explicit_correction`、訂正系 reason code。 |
| `確認が必要な追問` | 文脈引き継ぎ前に確認が必要な追問数。 | `clarify_before_carry`、`clarification_required`。 |

技術項目は以下のビジネス表示名に変換します。

| 技術項目 | 表示名 |
| --- | --- |
| `fallback_reason` | `失敗理由` |
| `state_action` | `状態処理` |
| `reason_signals` | `判定根拠` |
| `followup_offtopic` | `文脈外追問` |

これらの技術項目はエクスポートと BigQuery で確認可能にしますが、第一階層の UI カラムとして大量表示しません。

## 12. ユーザー詳細

画面名は `ユーザー詳細` とします。

`ユーザー一覧` の `詳細` から `/dashboard?user_id={user_id}` へ遷移します。初期表示は `今日` とし、選択肢は `過去3日`、`過去7日`、`過去14日`、`過去30日`、`過去60日`、`全部`、`カスタム` とします。

| セクション名 | 内容 |
| --- | --- |
| `ユーザーサマリー` | メッセージ数、回答成功、低カバレッジ、低評価、追問、suggestion 利用状況の主要カード。 |
| `利用推移` | 日別のメッセージ数、回答成功、低カバレッジ、feedback 推移。 |
| `利用モード分布` | `社内モード` / `Web検索モード` の分布。 |
| `回答品質分布` | `回答可能性`、`回答利用可能性`、`業務利用可能性`、`根拠十分性`。 |
| `追問状況` | 追問認識、追問成功率、訂正、確認要求。 |
| `会話一覧` | 左側 1/4 幅に表示する会話リスト。最大15件程度を一画面で見せ、スクロールで追加確認する。 |
| `メッセージ履歴` | 右側 3/4 幅に表示する選択会話のメッセージリスト。最大10件程度を一画面で見せ、縦横スクロールで追加確認する。 |

この画面では `エクスポート` から選択ユーザーの選択期間データを出力できるようにします。

## 13. 会話・メッセージ確認

`チャット記録確認` は独立した第一階層画面にはしません。ユーザー単位の確認フローを維持するため、`ユーザー詳細` で会話を選択した後に右側の `メッセージ履歴` として表示します。

内部的には `/api/trace/messages` を使用します。フロントエンドでは主に以下の条件をユーザー詳細から引き継ぎます。

```text
conversation_id
trace_id
turn_id
user_id
user_email
期間
状態
モード
```

グローバルな trace_id / turn_id 横断検索は MVP の第一階層 UI には置きません。必要な場合は export、BigQuery、または制限付き内部調査導線で利用します。

### 13.4 軽量監視タグ

| タグ表示名 | 条件 |

| `低カバレッジ` | message または turn が低カバレッジ条件に該当する。 |
| `低評価` | bad feedback が存在する。 |
| `追問` | follow-up turn に属する message。 |
| `エラー` | message または request にエラーがある。 |
| `要確認` | clarification、低 delivery readiness、schema/join 問題などが存在する。 |

## 14. バックエンド保持のみの詳細項目

以下の詳細 payload 群は BigQuery とエクスポートに保持しますが、MVP の第一階層画面には表示しません。

| 詳細項目グループ | 例 |
| --- | --- |
| Turn 詳細 | `query_hash`, `intent_family`, `primary_task_intent`, `route_path`, `final_channel_mix`, `structured_tasks`, `structured_hit_count`, `answer_usable`, `outcome`, `primary_reason_code` |
| Evidence 詳細 | `claim_spans`, `citation_index`, `citations`, `grounding.sources`, `source_trust_tier`, `verification_required`, `readable_locator`, `page` |
| Governance 詳細 | `answerability_level`, `usability_level`, `evidence_sufficiency`, `clarification_required`, `delivery_readiness`, `coverage_score`, `alignment_score`, `verification_verdict` |
| Follow-up 詳細 | `decision_normalized`, `anchor_turn_id`, `entity_lock_key`, `entity_lock_inherited`, `inherited_fields`, `dropped_fields`, `reason_codes` |
| Raw debug 詳細 | `raw_payload_json`, `schema_valid`, `schema_validation_errors` |

この方針により、管理者画面の可読性を維持しつつ、必要な調査証跡をエクスポートおよび運用調査で利用できるようにします。

## 15. データ健全性

`データ健全性` は MVP の独立フロントエンドページにはしません。

モニター上の判断に使うデータ自体が信頼できるかは重要ですが、非技術管理者向けの第一階層 UI では情報量が多く、通常の業務判断を妨げます。そのため、MVP では backend API、BigQuery、Cloud Logging、export、運用者向け内部確認に保持します。

| 表示名 | 目的 |
| --- | --- |
| `イベント件数` | event family と schema version ごとのイベント数を確認する。 |
| `必須項目欠落` | trace、request、conversation、turn、message、mode などの必須識別子の欠落を確認する。 |
| `Schema不一致` | 想定外または未対応の schema version を検出する。 |
| `Join健全性` | answer、message、follow-up、coverage gap のレコードが結合できるか確認する。 |
| `データ遅延` | source event time から monitor 反映までの遅延を確認する。 |

## 16. MVP実装範囲

MVP のフロントエンド実装範囲は以下とします。

| 領域 | MVP対象 |
| --- | --- |
| 第一階層 | `ダッシュボード` に集約する。 |
| KPIカード | `?` 説明付きの5カード。 |
| ダッシュボードグラフ | 利用環境・モード分析、利用推移、活性度分布、回答品質、連続質問分析。 |
| ユーザー一覧 | ダッシュボード下部に配置し、絞り込み、検索、エクスポート、ユーザー詳細リンクを提供する。 |
| ユーザー詳細 | サマリー、推移、モード分布、品質分布、追問状況、会話一覧、メッセージ drawer、エクスポート。 |
| 会話・メッセージ確認 | ユーザー詳細内で会話選択後に lazy load する。 |
| エクスポート | 期間と出力データのみを指定する設定モーダル。出力列はデータ種別ごとに固定する。 |

初回フロントエンドリリースでは以下を後続対応とします。

| 領域 | 理由 |
| --- | --- |
| Raw payload 全文ビューア | 管理者向け第一階層 UI には技術的すぎるため、BigQuery / export に保持する。 |
| Evidence 詳細ドロワー | 技術調査には有用だが、MVP 画面には情報量が多すぎる。 |
| Governance 詳細ドロワー | 管理者ワークフロー上の必要性が確認されるまでは backend / export 詳細に保持する。 |
| Workitem 管理UI | まず coverage gap の可視化を優先し、triage workflow は後続で追加する。 |
| 独立 `チャット記録確認` 画面 | ユーザー詳細のドリルダウンで十分なため、MVP では作らない。 |
| 独立 `データ健全性` 画面 | 技術運用者向け情報のため、MVP ではフロントエンドに出さない。 |
